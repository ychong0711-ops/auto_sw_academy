# 00. 큰 그림 — 역량 체인 지도와 학습법

## 왜 이 4단계가 "하나의 체인"인가

자동차 SW 엔지니어링 면접/실무에서 요구되는 역량은 서로 독립이 아니라 **누적**입니다:

```
  ① 임베디드 C/C++      : 레지스터·비트·메모리를 직접 다루는 손
        │ 없으면: MCAL 코드가 "주문"처럼 보임
  ② AUTOSAR (BSW/MCAL)  : 수십만 줄 ECU 코드를 구조화하는 뼈대
        │ 없으면: Com/Dcm 같은 모듈이 왜 있고 어디 끼는지 몰라 프로토콜 코드를
        │          "그냥 함수 뭉치"로 짬 → 유지보수 불가
  ③ 통신/진단 프로토콜   : CAN 프레임, ISO-TP, UDS 라는 ECU의 언어
        │ 없으면: 안전/보안이 "문서 작업"으로만 보임
  ④ 기능안전/보안/ASPICE : 그 언어로 "틀리지 않게, 뚫리지 않게, 증명 가능하게"
        └ 바로 실무(BSW 개발·진단 개발·기능안전 엔지니어)의 일상
```

## 체인 ↔ 현업 매핑

| 단계 | 이 저장소 | 현업 직무/업무 | 현업 도구 |
|---|---|---|---|
| ① | ex1 (비트, 레지스터 맵, 링버퍼, Q포맷, 상태기계) | 모든 임베디드 직군의 공통 기초 | gcc, Lauterbach, 데이터시트 |
| ② | ex2 (SimMcu/Dio/Adc/Can → CanIf/PduR/Com → RTE → SWC) | **BSW/MCAL 개발자**, SWC 개발자 | EB tresos, Vector DaVinci, ARXML |
| ③ | ex3 (신호 코덱, ISO-TP, UDS) | **통신/진단 개발자**, 캘리브레이션 | CANoe, CAN.DiVa, DBC/ODX |
| ④ | ex4 (CRC, E2E, AES/CMAC, SecOC, WdgM, ASPICE 산출물) | **기능안전/보안 엔지니어**, SW 아키텍트, ASPICE 대응 | HSM 개발킷, DOORS, 정적분석 |

## 학습 순서 (권장: 단계당 1~2일)

1. `make` 로 전체 빌드 → `make check` 가 전부 PASS 인 것 확인 (환경 점검)
2. **ex1**: 코드 읽고 → 각 파일의 "연습문제" TODO 수행 → 테스트 다시 PASS
3. **ex2**: `docs/02` 의 계층도를 본 뒤, 시그널 흐름 테스트(`test_ex2_signal_flow.c`)의 주석 경로대로 함수를 따라가며 브레이크포인트 없이 "타고 가는 연습"
4. **ex3**: `docs/03` 의 표를 본 뒤 테스트를 먼저 읽기(스펙을 테스트로 읽는 습관). UDS 는 실제 진단기 로그와 1:1 로 대조해 보기
5. **ex4**: 오류 주입 테스트(FI-01~05)에 주목 — "정상 동작"보다 "위반을 잡는 코드"가 안전/보안의 본질
6. **capstone**: 전체 출력을 한 장의 시퀀스 다이어그램으로 직접 그려보기 (면접에서 설명할 수 있어야 함)
7. **ASPICE 연습**: 임의 요구사항을 하나 추가해 SRS 태그→코드→TC→traceability_matrix.csv 갱신까지 한 세트로 수행

## 완료 기준 (스스로 채점)

- [ ] EX1 의 모든 매크로/함수를 **보지 않고** 쓸 수 있다
- [ ] EX2 에 "새 CAN 프레임 + 신호"를 추가할 때 **고쳐야 할 파일 목록**을 외우고 있다 (힌트: Cfg 테이블뿐이어야 함)
- [ ] 0x7DF 로 날아온 "10 03" 이 ECU 안에서 거치는 함수 호출 순서를 말할 수 있다
- [ ] NRC 0x13/0x33/0x36/0x37 의 차이와 발생 조건을 설명할 수 있다
- [ ] E2E(안전)와 SecOC(보안)가 **왜 둘 다 필요한지** 설명할 수 있다
- [ ] 임의의 SRS 번호에서 TC까지 추적할 수 있다
