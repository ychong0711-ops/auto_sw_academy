# 01. 임베디드 C/C++ — 손에 익혀야 할 5가지

책 한 권 분량의 내용을 "AUTOSAR 에서 실제로 쓰이는 형태"만 추려 5개 실습으로 압축했습니다.
각 파일은 독립 실행되며, 테스트가 곧 예제 문서입니다.

## EX1-1 비트 연산 (`ex1_1_bit_ops.c`)

- 레지스터는 "32개의 스위치". SET/CLR/TGL/GET 매크로와 **필드(pos,width) 개념** 은 MCAL 코드의 일상
- **중요**: 비트 연산은 항상 `unsigned` 타입에서. 부호 있는 시프트는 구현 정의(implementation-defined) — MISRA-C:2012 Rule 10.x 가 금지하는 이유
- `1u << n` 의 `u` 가 없으면 `1 << 31` 은 음수 → UB. 이 하나로 과거 수많은 리콜급 버그가 났습니다

**연습**: `field_set` 이 width=32 일 때 왜 위험한지 설명하고 방어 코드를 추가하세요.

## EX1-2 레지스터 맵 & volatile (`ex1_2_register_map.c`)

- 실제 MCU 헤더(`stm32f4xx.h` 같은)의 본질: 구조체를 주변장치 주소에 캐스팅
- `volatile` 의 의미: "이 메모리는 컴파일러 모르게 바뀐다" — 하드웨어가 바꾸거나, ISR이 바꾸기 때문
- **volatile ≠ 동기화**: 멀티태스크 경쟁은 별도 메커니즘(원자적 연산, 마스크)이 필요. BSRR(1쓰면 set) 같은 레지스터가 존재하는 이유가 RMW 경쟁 때문

**연습**: 이 파일의 `BSRR` 하드웨어 모델 주석을 읽고, `ODR |= mask` 방식과의 차이를 설명하세요.
(힌트: ISR 이 중간에 끼어들면?)

## EX1-3 링 버퍼 (`ex1_3_ring_buffer.c`)

- ISR(생산자)→메인(소비자) 단방향 통신의 사실상 표준. AUTOSAR Com 수신 큐, UDS 바이트 스트림 처리에 그대로 등장
- `head`/`tail` 에 volatile 이 필요한 이유: 서로 다른 문맥이 갱신
- "한 칸 희생" 규칙: `(head+1)%N == tail` 이면 full — 유실 카운트를 두는 습관(Dem 오류 카운팅의 씨앗)

**연습**: 수용량 N-1 을 N 으로 늘리려면 어떤 상태 변수가 더 필요한지 구현해 보세요.

## EX1-4 고정소수점 (`ex1_4_fixed_point.c`)

- FPU 없는 저가 MCU 에서의 실수 연산 표준: **Q 포맷**
- "**factor/offset + raw**" 개념은 EX3 의 CAN 신호 물리량 변환과 **동일한 사고방식** — AUTOSAR ComSignal 의 `ComFactor/ComOffset` 이 바로 이것
- 64비트 중간 결과 없이 Q 곱셈을 짜면 조용히 깨진다 (TC_FX_010_03)

**연습**: Q16.16 의 표현 범위를 계산하고, saturate 버전 `q_mul_sat` 를 작성하세요.

## EX1-5 상태기계 (`ex1_5_state_machine.c`)

- Dcm(세션), CanSM(통신 상태), WdgM(감시 상태), BswM(모드 관리)… AUTOSAR BSW 는 상태기계 박람회
- 패턴: **상태 × 이벤트 → 다음 상태 + 출력**. 출력은 상태의 함수로만
- 정의되지 않은 이벤트를 "그냥 무시"하는 게 안전 설계의 첫걸음 (TC_SM_010)

**연습**: `EV_KEY_ON` 상태에서 문이 열리면 경고등을 켜는 기능을 상태 1개 + 이벤트 2개로 확장해 보세요.
