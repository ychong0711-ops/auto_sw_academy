Auto SW Academy — 사용자 가이드

Auto SW Academy는 AUTOSAR 기반 자동차 SW 개발자의 역량 체인을 실제 코드로 빌드하고, 실행하고, 디버깅하며 익히는 핸즈온 교육 프로젝트입니다. 모든 코드는 PC의 gcc / MSYS2 환경에서 실행되며, 별도의 임베디드 타겟 보드가 필요하지 않습니다.

목표: 임베디드 C → AUTOSAR BSW/MCAL → 자동차 통신/진단(UDS, ISO-TP) → 기능안전/보안(E2E, SecOC, Wdgm)까지 4단계 역량 체인을 한 저장소에서 경험합니다.

Windows (MSYS2) 가이드

주의: GCC는 MSYS2의 /mingw64/bin/에 있습니다. MSYSTEM=MINGW64 환경변수와 함께 bash를 실행해야 합니다.

MSYS2 설치 및 빌드:

# 1. MSYS2 설치 (https://www.msys2.org)
# 2. MINGW64 업데이트 및 도구 설치
pacman -Syu
pacman -S mingw-w64-x86_64-gcc make python3 python3-pip

# 3. cantools 설치 (선택)
pip install cantools

# 4. MINGW64 환경에서 빌드
#    Windows Terminal/PowerShell에서:
$env:MSYSTEM="MINGW64"
$env:CHERE_INVOKING="yes"
C:\msys64\usr\bin\bash.exe -l -c "cd /c/java-learning/auto_sw_academy && make -j4"

Windows 전용 스크립트:

# PowerShell에서 전체 파이프라인 실행
.\run_all.ps1

run_all.ps1은 MSYS2 MINGW64 bash를 경유하여 빌드 → 테스트 → capstone → trace-check까지 한 번에 실행합니다. run_all.sh의 Windows 버전입니다.

3. 빌드 시스템

두 가지 빌드 시스템을 제공합니다. 기본은 GNU Make이며, CMake는 IDE 통합이나 크로스 플랫폼이 필요할 때 사용합니다.

3.1 Makefile — 주요 타겟

명령설명
make / make all설정 생성 + 19개 타겟 전체 빌드
make -jNN개 병렬 잡으로 빌드 (예: -j4)
make check전체 테스트 18종 순차 실행
make cleanbuild/ 및 logs/ 삭제
make gen설정 생성기만 실행 (config/ecu.json → generated/)
make tracecapstone 실행 → 트레이스 기록 → DBC 디코드
make trace-checktrace + cantools vs stdlib 디코드 일치 자동 검증
make analyzecppcheck 정적 분석 (전체 소스)
make strict-Werror 모드 빌드 (경고→에러)
make formatclang-format으로 전체 소스 포맷팅
헤더 의존성 자동 추적: Makefile은 -MMD -MP 플래그를 사용하여 헤더 파일이 변경될 때 자동으로 재컴파일합니다. 별도의 의존성 관리가 필요 없습니다.

3.2 CMake

mkdir build-cmake && cd build-cmake
cmake ..
cmake --build .
ctest --output-on-failure

CMakeLists.txt는 Makefile과 동일한 18개 테스트 타겟을 정의합니다. add_custom_command로 Python 설정 생성기를 자동 실행하며, enable_testing() + add_test()로 ctest 통합을 제공합니다.

5. EX1 — 임베디드 C 기초

ex1_embedded_c/는 자동차 SW 개발에 필요한 C/C++ 핵심 역량을 8개 독립 모듈(C 5종 + C++ 3종)로 구성합니다. 각 모듈은 단일 .c/.cpp 파일로 작성되어 개별 빌드 및 테스트가 가능합니다.

ex1_1_bit_ops

비트 set/clear/toggle, 비트 필드 읽기/쓰기, popcount. MCAL 레지스터 조작의 기초.

ex1_2_register_map

구조체 기반 레지스터 맵, BSRR을 통한 RMW 원자성, volatile 의미.

ex1_3_ring_buffer

ISR-메인루프간 동기화에 사용되는 고정 크기 FIFO. 가득 참/유실 처리, wrap-around 정합성.

ex1_4_fixed_point

Q16.16 고정소수점 연산 (int64 중간결과). 물리량↔raw 변환 (factor/offset 방식).

ex1_5_state_machine

차량 시동 시퀀스 상태기계 (OFF→ACC→ON→CRANK→RUN). 무효 전이 차단, 이벤트 기반 전환.

ex1_6_cpp_state_machine

C++ 템플릿 기반 상태기계 (열거형 + std::array 전이표). 객체지향 캡슐화, constexpr 특성, 템플릿 메타프로그래밍의 기초.

ex1_7_cpp_template_buffer

C++ 템플릿 RingBuffer<T, N>. 타입/크기 독립 FIFO, RAII 자원 관리, 템플릿 특수화, noexcept 보증.

ex1_8_cpp_fixed_point

C++ Q16.16 FixedPoint 클래스. 연산자 오버로딩, 형변환, constexpr 생성자, 단위 테스트 14개.

# 개별 실행
./build/ex1_1_bit_ops
./build/ex1_2_register_map
# ...

7. EX3 — 통신 및 진단

ex3_comm_diag/는 자동차 네트워크 통신 프로토콜 3종과 UDS 진단 프로토콜을 다룹니다.

CAN 신호 (ex3_can_signal)

CAN 프레임 내 시그널 패킹/언패킹 — Intel(Little-Endian)과 Motorola(Big-Endian) 두 가지 바이트 순서를 지원합니다. DBC 정의와 동일한 비트 레이아웃 규칙을 따릅니다.

  • 시작 비트(start bit) + 길이 기반 인코딩
  • 바이트 경계 교차 시그널 처리
  • 물리량 변환 (factor × raw + offset)
  • 범위 검증 (프레임 밖/32비트 초과 거부)

ISO-TP (ex3_isotp)

ISO 15765-2 Transport Protocol 구현:

  • SF (Single Frame): 1-7 바이트 단일 프레임
  • FF (First Frame) + FC (Flow Control) + CF (Consecutive Frame): 8+ 바이트 다중 프레임
  • STmin: 연속 프레임 간 최소 간격 ( pacing )
  • 오류 주입: 시퀀스 번호 불일치 → abort, FC Overflow → abort

UDS (ex3_uds)

ISO 14229-1 Unified Diagnostic Services 서버 구현. 지원 서비스:

SID서비스설명
0x10DiagnosticSessionControlDefault / Extended / S3 타임아웃
0x11ECUResethardReset
0x14ClearDiagnosticInformationDTC 삭제 (보안 게이트)
0x19ReadDTCInformationreportDTCByStatusMask
0x22ReadDataByIdentifierDID 기반 데이터 읽기 (VIN 등)
0x27SecurityAccessSeed&Key 인증 (잠금/해제)
0x2EWriteDataByIdentifierDID 데이터 쓰기
0x31RoutineControl자기진단 루틴 (조건 검사 포함)
0x3ETesterPresent세션 유지

NRC (Negative Response Code) 처리: 0x11(미지원), 0x12(세션), 0x13(길이), 0x22(조건), 0x31(보안), 0x33(보안), 0x35/36/37(키 실패/지연) 등 실제 UDS 스펙을 따릅니다.

8. EX4 — 기능안전 및 보안

ex4_safety_security/는 ISO 26262 기능안전과 SECURITY 메커니즘을 구현합니다.

CRC-8 / E2E Profile 1 (ex4_crc_e2e)

  • CRC-8 SAE J1850 — 검증 벡터 포함
  • AUTOSAR E2E Profile 1: Counter 기반 시퀀스 검사
  • 상태 분류: INITIAL → OK → REPEATED → OKSOMELOST → WRONGSEQUENCE → ERROR
  • 데이터 오염(CRC/DataID 불일치) 탐지

AES-128 / CMAC / SecOC (ex4_secoc)

  • AES-128 ECB (FIPS-197 검증 벡터 일치)
  • AES-CMAC (RFC 4493 Example 1, 2 일치)
  • SecOC: 신선도 카운터 + MAC 기반 PDU 인증
  • 재전송 공격 방어 (같은 프레임 거부)
  • 위조 공격 방어 (MAC 불일치 거부)
주의: 본 프로젝트의 암호 구현은 교육용입니다. 양산 ECU에는 검증된 암호 라이브러리/HSM을 사용하세요.

Watchdog Manager (ex4_wdg)

  • 멀티 SE(Supervised Entity) 관리
  • Alive 감독 (주기적 체크포인트)
  • SE 행업 → EXPIRED 상태 전파
  • 글로벌 위반 누적, 리셋 필요 조건

ASPICE 산출물

ex4_safety_security/aspice/ 디렉터리에는 SWE.1~SWE.6 프로세스에 대응하는 추적성 매트릭스(SRS↔함수↔TC)가 포함되어 있습니다.

9. 통합 데모 (Capstone)

capstone_demo는 EX1~EX4의 모든 요소를 하나의 시나리오로 묶은 종합 데모입니다. 가상 ECU와 진단기 간의 전체 통신 체인을 시연합니다.

시나리오 흐름

PHASE 1: 주기 프레임 송신
  ─ VehicleState (0x100) 3회 — DBC 신호 패킹
  ─ SecOC 보호 프레임 (0x180) — 신선도 + MAC

PHASE 2: 진단기가 프레임 검증
  ─ SecOC 인증 성공
  ─ 재전송 공격 → 거부 ✔
  ─ 위조 프레임 주입 → 거부 ✔
  ─ E2E 체크: INITIAL / OK / ERROR

PHASE 3: UDS 진단 워크플로 (ISO-TP)
  ─ VIN 읽기 → 확장 세션 → SecurityAccess(Seed&Key)
  ─ WriteDID → ReadDID 확인
  ─ DTC 판독 → ClearDTC
  ─ ECU hard reset

PHASE 4: Watchdog 행업 검출
  ─ 통신 러너블 60ms 생존 보고 중단
  ─ WdgM → EXPIRED → MCU 리셋 트리거

실행

# 기본 실행
./build/capstone_demo

# 트레이스 로그 기록 (make trace-check에서 사용)
./build/capstone_demo --trace logs/capstone_trace.log

11. 트레이스 DBC 디코드 (경로 C: 미니 CANoe 워크플로)

CANoe의 Trace 창 핵심 기능(버스 트레이스 기록 + DBC 신호 해석)을 무료 도구만으로 재현합니다. 이중 디코드 엔진으로 정확성을 검증합니다:

엔진기반특징
cantoolsPython 오픈소스 DBC 파서실무 표준, DBC 정식 지원
--stdlib자체 구현 파서경량, 의존성 없음, 교육용

워크플로

# 1. capstone 실행 → 버스 트레이스 로그 생성
./build/capstone_demo --trace logs/capstone_trace.log

# 2. 생성된 VehicleNetwork.dbc 로 신호 디코드
python3 tools/decode_trace.py generated/VehicleNetwork.dbc logs/capstone_trace.log

# 3. 또는 한방에: 두 엔진 출력 비교까지 자동 검증
make trace-check

출력 예시

[      0 ms] 0x100 VehicleState (8B, 송신:ECU)  80 10 00 00 00 00 00 00
                        BatteryVoltage = 12.8 V   (raw=128, [0..409.5] V)
                        LightSwitch = 1 ; HeadlightCmd = 0
[      0 ms] 0x180 RAW  ... (DBC 미등록 ID)   ← SecOC 보호 프레임
[      9 ms] 0x7E0 RAW  ...                  ← ISO-TP/UDS 진단 프레임
== 요약 == 총 32 프레임 | DBC 해석 3 | RAW 29
실무 포인트: DBC는 애플리케이션 신호 설계 산출물입니다. SecOC로 보호된 PDU나 진단 프레임(ISO-TP/UDS)은 DBC만으로 해석되지 않습니다 (진단은 ODX/PDX가 담당). 이 한계가 trace 출력에 그대로 나타납니다.

14. FAQ

Q: Windows에서 "cc: command not found" 오류가 발생합니다.

GCC가 MSYS2의 /mingw64/bin/에만 설치되어 있기 때문입니다. MSYSTEM=MINGW64 환경변수를 설정하고 bash를 실행하거나, run_all.ps1을 사용하세요.

Q: make clean을 해도 generated/ 파일이 남아 있습니다.

generated/는 설정 생성기의 출력입니다. 수동으로 삭제하려면 rm -rf generated/를 실행하고, make로 재생성하세요.

Q: 새 CAN 프레임이나 시그널을 추가하려면 어떻게 하나요?

config/ecu.json에 프레임과 시그널을 추가한 후 make clean && make로 재빌드하세요. 설정 생성기가 자동으로 C 코드, DBC, 문서를 재생성합니다.

Q: 테스트를 추가하고 싶습니다.

(1) ex2_mini_autosar/test/ 등 적절한 test 디렉터리에 test_exN_xxx.c 생성. (2) Makefile의 TARGETS 목록에 $(BUILD)/exN_xxx 추가 + 빌드 규칙 작성. (3) CMakeLists.txt의 foreach 루프에 이름 추가. (4) make check로 검증.

Q: DBC 파일을 CANoe에서 사용할 수 있나요?

네. generated/VehicleNetwork.dbc는 표준 DBC 형식이므로 CANoe, CANalyzer, PCAN-View 등 DBC 호환 도구에서 직접 불러올 수 있습니다.

Q: 이 코드를 실제 ECU에 포팅할 수 있나요?

구조는 AUTOSAR 아키텍처를 따르지만, MCAL(SimMcu)을 실제 MCU 드라이버로 교체해야 합니다. porting/stm32/stm32_porting_guide.md에 STM32 보드 포팅 가이드가 있습니다. 암호 구현은 교육용이므로 양산 시 검증된 라이브러리로 교체하세요.
